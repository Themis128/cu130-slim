# Cline Custom Instructions
# Add this to Cline Settings → Custom Instructions
# Or create .clinerules in your project root

---

## General Behavior

- **Be concise** - Prefer minimal, focused responses over verbose explanations
- **Show code first** - Lead with implementation, explain after if needed
- **No unnecessary comments** - Code should be self-documenting
- **Follow existing patterns** - Match the codebase's style, naming, architecture

## Planning (Plan Mode)

- Break complex tasks into **small, verifiable steps**
- Identify **risks and unknowns** upfront
- Prefer **incremental changes** over big rewrites
- Ask for clarification on **ambiguous requirements** before acting

## Acting (Act Mode)

- **One file at a time** - Complete each change before moving on
- **Run tests/lint** after each logical change
- **Commit logically** - Group related changes
- **Don't over-engineer** - Solve the immediate problem

## Code Style

- **TypeScript/JS**: Use `const`/`let`, prefer `type` over `interface`, explicit return types for public APIs
- **Python**: Type hints on all functions, `pathlib` over `os.path`, `pytest` for tests
- **Rust**: `clippy` clean, explicit error handling, avoid `unwrap()` in production
- **Go**: Standard library first, `gofmt` formatted, table-driven tests

## File Operations

- **Read before write** - Understand existing code first
- **Minimal diffs** - Change only what's necessary
- **Preserve formatting** - Match indentation, line endings, quote style
- **No generated code in repo** - Build artifacts go in `.gitignore`

## Token Optimization

- **Use .clineignore** - Exclude node_modules, build, cache, media, large data
- **Reference files by path** - Don't paste large files unless necessary
- **Summarize context** - "File X does Y" vs pasting 500 lines
- **Clear history** - Start fresh conversations for new tasks

## Error Handling

- **Fail fast** - Validate inputs early
- **Descriptive errors** - Include context: what, where, why
- **Log at appropriate level** - Debug for dev, warn/error for prod
- **Don't swallow exceptions** - Let them bubble or handle explicitly

## Git Workflow

- **Conventional commits**: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`
- **Small commits** - One logical change per commit
- **Meaningful messages** - What and why, not how
- **Branch naming**: `feat/description`, `fix/description`, `refactor/description`

## Testing

- **Write tests for bugs** - Regression test first
- **Test behavior, not implementation** - Public API contracts
- **Edge cases**: empty, null, boundary, error conditions
- **Fast tests** - Unit > integration > e2e

## Performance

- **Profile before optimizing** - Measure first
- **Avoid premature abstraction** - YAGNI
- **Cache at the right layer** - HTTP, DB, compute
- **Monitor token usage** - Check Cline's token counter

## Security

- **Never commit secrets** - Use env vars, secret managers
- **Validate all inputs** - Sanitize, escape, parameterize
- **Least privilege** - Minimal permissions for tokens/keys
- **Audit dependencies** - `npm audit`, `cargo audit`, `pip-audit`
